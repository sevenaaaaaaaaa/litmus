# P1-03 · 五动作规格

> 看板 DoD：每个动作有快捷键、落点、失败行为；两个输入方式等价。

## 做法：规格即代码

不写一份"交互文档"然后等它和实现漂移。五个动作写进 [actions.spec.json](reference/p1-03-actions/actions.spec.json)，由 [actions.mjs](reference/p1-03-actions/actions.mjs) 校验、生成速查表：

```
node action-cli.mjs validate          # VALID 5 个动作 / 5 个状态
node action-cli.mjs sheet --out dist/reference.md
```

校验器管六件事：**键位冲突、保留键、落点是否合法、写盘必须可撤销且保稿、失败必须不静默、埋点必须真的存在**。它抓到的两个问题都是"人读不出来"的那种（见下）。

## 五动作

| 动作 | Mac | Web | iPhone | 落点 | 撤销 | 双向可达 | 失败时说什么 |
|---|---|---|---|---|---|---|---|
| **落下** | `⌥Space` | `Enter`（输入框内） | 分享扩展 / Action Button / 锁屏 | 新卡（当前空间，兜底 Inbox） | 可撤销 | 3/3 | 没写成，内容还在输入框里 |
| **连上** | `⌘⇧↩` | `⌘⇧↩` | 长按卡 → 连到 | 一条真实 wikilink + 画布边 | 可撤销 | 3/3 | 这两张连不上：目标卡可能已删除 |
| **翻开** | `Space` | `Space` | 上滑卡面 / 长按预览 | 视图（不改数据） | 不可撤销（无需） | 2/2 | 这张卡的来源还没索引好，稍等一下就回来 |
| **推进** | `⌘↩` | `⌘↩` | 长按 → 推进 / 阅读器内提问 | 候选卡（不写盘）→ 确认后新卡并连回 | 可撤销 | 4/4 | 这次没生成出来，范围和你的输入都还在 |
| **发布** | `⌘⇧P` | `⌘⇧P` | 分享 → 发布 | 页面 / HTML / llms.txt | 可撤销（撤回） | 3/3 | 没发出去：先检查发布前体检，页面还没生成 |

|---|---|---|

| 有据 | 推进（counter） | 找反例 |

## 「两个输入方式等价」怎么变成可验证的

原来的 DoD 说"等价"，但那是一句形容词。现在每个动作列出**操作级能力**，每条都必须 keyboard=true 且 pointer=true：

- 落下：打开快捕 / 提交 / 取消
- 连上：开始连线 / 选目标 / 取消
- 翻开：翻开 / 合上
- 推进：开启 / 取消候选 / 确认落盘 / 重试
- 发布：打开面板 / 确认 / 取消

共 **15 个操作，15/15 双向可达**。少一个就报错——"取消只能用鼠标"这种缺陷不会留到实现阶段。

## 校验器抓到的两个真问题

1. **Web 上 `⌘↩` 撞车。** 我给"落下"和"推进"都写了 `mod+enter`，规范化后是同一条键。改法：输入框里 `Enter` 就是提交，`⌘↩` 留给推进——语义也更对。
2. **连上会写盘，却没写"失败保稿"。** 规则说写盘动作必须保稿，规格里 `preserveInput: false`。已改 true：连线失败时选中的卡与目标不能丢。

这两条都属于"文档里读不出来、跑一遍才知道"的类型，所以规格必须能被程序读。

## 边界

- **没做 UI**：这是规格 + 校验器 + 速查表，不是实现。
- **iOS 没有键位**：系统没有全局热键，`keys.ios` 为空是刻意的；触控方式必须至少两种（已检查）。
- **手势冲突未检测**：上滑/长按与系统手势的冲突要真机。
- **系统级快捷键冲突未检测**：`⌥Space` 可能撞 Spotlight 或输入法，需要真机清单。
- **删除 / 归档不在五动作里**：它们走回收站，规则还没写（见新思路 4）。

## 新思路

1. **键位是公共资源，需要一张全局表。** 现在只查内部冲突与保留键；真正的冲突在系统层（`⌥Space` 与 Spotlight、输入法切换）。应该在设置里提供"冲突检测"按钮，并且在首次启动时试一次注册、失败就换键。
2. **失败文案要按原因分，不能一句话包打天下。** 磁盘满、没权限、同步中、AI 超时——用户要做的动作完全不同。spec 应该升级成 `failure.causes[]`，每类一句。
3. **等价现在只验"能不能触发"，没验"结果是否一致"。** 键盘取消和鼠标取消是否回滚同样的状态？需要一条"两条路径产生同一串事件"的测试（P1-05 有真实现时才能做）。
4. **删除/归档是唯一没有失败行为的动作，而它最需要。** 建议明确：删除不进五动作，走回收站 + 7 天保留 + 撤销；这条要写进 P1-04 的协议，否则"任何删除都可撤销"只是口号。
5. **速查表应该由 spec 生成到界面里。** 菜单、tooltip、帮助页的键位都从这份 JSON 渲染；谁手写键位，谁就负责漂移。

## 对后续的影响

- **P1-04 推进闭环协议**：直接用 `advance.ops` 的四个操作定义状态机（开启 / 取消 / 确认 / 重试），不另起一套词。
- **P1-05 参考实现**：落盘前跑 `verifyClaim`（P1-11），失败按 spec 的 `failure` 分支处理，埋点按 `telemetry` 列表打。
