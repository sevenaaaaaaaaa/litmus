## 二、把八条压成三条主线

这三条不是重复上面，而是上面八条共同指向的东西。它们会进 L3 的重规划。

### 主线 A · 可追溯性不是功能，是地基

孤儿事件、张力没有门牌、卡背锚点、队列没有回执——看起来是四件不相干的事，其实是同一件：**产品里每一个"结论"都必须能指回它的来处，或者明说没有来处**。
规划把它写成 §4.2「证据优先」的一个功能；这轮做完发现它是数据结构问题（锚点、attempt_id、ack、block anchor），必须在 Phase 1 的数据模型里就定死，不能留到 Phase 2 再补功能。

### 主线 B · 产品里有两套时钟，混用就出体验问题

- 人的时钟：3 秒落下、30 秒推进、一次确认发布。
- 系统的时钟：AI 首 token、同步往返、上传、索引重建。

本轮所有卡点都在"把系统时钟塞进人的时钟"：分诊阻塞保存、上传阻塞"已保存"、索引阻塞输入、AI 阻塞交互。
**结论：任何一个动作的"成功"只能由本地写盘判定；一切远端都是后置状态。** 这句话应该写进 P1-03 的交互纪律。

### 主线 C · 减法必须先有度量

规划说"每季度删一个入口、合并一个页面、去掉一个指标"，但没有入口使用率就没有依据。本轮做减法清单时，四项里有两项找不到任何数据支撑（文档库入口、检查器常驻）。
**结论：`ui.entry_used` 应该先于减法上线。** 顺序错了，减法就是赌博。
